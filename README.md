# Artefact AI Engineer challenge

## Data quality increment

The loader reads six canonical CSVs into a single immutable snapshot. It checks CSV headers and row shape, identifiers, duplicate keys, references, ISO dates, product/order states, finite nonnegative `Decimal` amounts, promotion bounds and flags, positive quantities and JSON objects (including duplicate keys). A structural error rejects the entire snapshot. No source file is modified. Run on the original challenge directory with exact approved SHA-256 verification:

```powershell
python -m artefact.report 'C:\App\Artefact\Desafio Técnico AI Engineer 2026\data' --baseline
```

The report contains table counts, hashes and field-level product findings with evidence and confidence; it does not include customer or order records. Treat reports as internal because they describe the private dataset. For synthetic input, omit `--baseline` and use the canonical filenames (`products.csv`, etc.). Run tests using `python -m unittest discover -s tests`. Tests use synthetic data; the baseline integration test is skipped when the local originals are unavailable.

The deterministic scanner currently detects selected brand discrepancies, keyboard/string count disagreements and some category/title disagreements. Its controlled vocabulary and patterns are deliberately conservative and **not exhaustive**; absence of a finding is not a guarantee of semantic correctness. Descriptive issues never invalidate independently typed price or stock. They do not correct the source, establish which field is true, or implement a seller handoff.

The source dataset and restricted documents are excluded from this public repository. Python standard library is sufficient for this increment.

## Commercial rules (incremental)

`artefact.commercial` implements the approved demo boundaries: metropolitan shipping is R$35 below R$500 and free at or above R$500; an unconfirmed other destination requires a quote. Installment eligibility uses per-installment floors of R$50 for 1–3, R$80 for 4–6 and R$100 for 7–12 installments. This follows the approved specific tier rules. PIX gives 5% off only when no promotion has already been applied. These functions do not infer a customer's location, promotion eligibility or historical order values.

Commercial product replies now include a server-calculated quote from the selected catalog snapshot. A single active promotion is applied to the registered product price using `Decimal` and cent rounding; PIX is calculated only when no promotion is present. Conflicting promotions, missing prices, zero stock and non-active products do not receive an offered final price. Snapshot promotion flags do not prove live validity, which is stated in replies. For product installment requests, the tool may supply only the explicitly requested count; Python applies it to the snapshot checkout price. For an amount stated by the customer, the installment tool arguments are checked against one unambiguous currency amount and count in the user's text. Historical order totals are not treated as new product amounts. Parts are split in cents without changing their sum, checked against the per-installment floor, and a valid alternative is shown when one exists. All replies remain deterministic after one provider selection; no second model inference performs or rewrites calculations.

The installment parser distinguishes a stated amount per part (for example, `3x de R$ 150`) from a total (`R$ 150 em 3x`), and Python derives the total before quoting. The tool supplies the amount actually stated by the customer, not a model-calculated total. A small, typed in-memory context per chat stores the relevant amount and its role, a uniquely resolved product, origin and turn. An unambiguous follow-up such as `esse valor em 3x` or `e em 3x` can use the prior total; a change of topic, multiple amounts or ambiguity between budget and product price requires clarification. A per-installment amount is not silently reused as a total. Context is bounded, isolated per chat and lost on restart. Sentence-ending punctuation is accepted without changing internal separators.

Warranty answers do not assume a manufacturer term without product-specific certificate evidence or treat the end of a commercial period as removal of legal rights. The acceptance scenario for online regret describes the request window and the need to confirm case conditions; it does not claim a return was approved or initiated. Policy wording is limited to user-approved demo decisions and acceptance criteria, not the restricted manual.

## Read-only demo services

`Catalog` searches by name, exposes typed commercial fields and masks a description or individual specification when the scanner flags a conflict. Availability means `active` and positive stock; promotion flags describe only the source snapshot, with ambiguous active promotions explicitly reported. Unflagged fields are not guaranteed correct because scanning is not exhaustive.

Search requires a nonempty name, category, price bound or explicit availability filter. Unfiltered listing is available only through an explicit recommendation request. Budget bounds and price-based recommendation ordering use the snapshot checkout price: the promotional price when exactly one active promotion applies, otherwise the registered price. An unknown checkout price, including conflicting promotions, cannot satisfy a budget filter. Pix is not assumed for budget eligibility and never accumulates with a promotion. The price and promotion are snapshot data and current validity remains unconfirmed. Proposed names, categories, identifiers and price bounds are checked against the current user request or a uniquely resolved product reference. This grounding is intentionally conservative: unfamiliar synonyms and genuinely ambiguous references may require clarification. Recommendation results are labelled as alternatives.

The six verified baseline files contained no values with more than two decimal places in their 65 product prices or 20 order totals at the time of inspection. The general CSV loader and administrative product uploads reject currency precision beyond cents, avoiding a price that loads but cannot be quoted or an order total the renderer cannot represent. No source data is changed or rounded to hide this distinction; discount percentages retain their own precision and are not treated as currency.

`OrderService` is restricted to the challenge's fictional data: an exact normalized unique full-name match returns only selected order fields and recorded totals, never recalculated current prices. A name is not authentication and this interface must not be used for real customer data. Policies are short demo decisions attributed to ARTEFACT-11, not the restricted manual or a claim of current store policy.

For a fictional order follow-up, an explicitly stated unique name may be resolved to a customer ID in the bounded in-memory context; the typed state stores the ID, not the name. A subject or identification change clears that reference. This is continuity for the fictional challenge data, not authentication for real customers.

Policy provenance: the demo's shipping, installments, Pix, defect/exchange and warranty interpretations and the two demo contacts are recorded as human decisions in ARTEFACT-11 (including the final approval/retifications). Saturday and Sunday/holiday hours come from acceptance cases A03/A04 in ARTEFACT-12, not an independently verified current schedule. The private manual is not included. Approval to implement these decisions and use a public repository does not independently establish permission from the document owner to publish every policy-derived summary; obtain that confirmation before final submission. These summaries were already public before PR #7.

## Telegram and LLM demonstration (experimental)

The optional demo uses Telegram long polling and a Responses API tool-selection request: the model selects tools and the server validates and executes them. Commercial and policy replies are rendered immediately and deterministically from returned fields, without a second inference. Order status is explicitly identified as a recorded status, separate from actual delivery date; payment method does not imply payment confirmation. At most three distinct read-only tools and one model call are allowed per data-backed turn; greetings need no model call. Conversation history is bounded, separated by private chat, memory-only and lost on restart. Human evaluation remains necessary. It is a fictional-data demonstration, not authentication for real customers. The original files are mounted read-only and checked against the approved hashes.

The review-writing tool must be the only tool in a turn. A confirmed write remains confirmed even if subsequent rendering fails; a timeout or invalid response from the review service is reported as an uncertain outcome, with a request to contact the store before retrying. No external message to a seller is implied. The Responses runtime optionally accepts a positive `TELEGRAM_ALLOWED_CHAT_ID`; when configured, other chats are ignored. Its absence preserves the existing unrestricted private-chat behavior and generates a configuration warning. Do not share that runtime without an explicit access decision. The Windows Codex demo continues to require its allowlist at startup.

Operational events use the standard Python logger `artefact.operations`: JSON fields include a random operation ID, component, stage, category, result, optional exception type and duration, and side-effect state. Correlation spans Telegram handling and conversation execution. Runtime entry points enable these logs on stderr; embedding applications may configure the logger themselves. They exclude message text, prompts, token values, chat IDs and exception messages. For example, a provider timeout produces an event with `category=provider`, `stage=provider`, `exception_type=TimeoutError` and `side_effect=none`; a failed review submission is marked `side_effect=unknown` because it might already have committed.

The conversation distinguishes a stated spending cap from a purchase total; a cap alone is not authority to calculate installments. Policy topics and excluded product mentions are checked against the current turn before tool execution. The language checks are conservative and may request clarification for unsupported wording. If a review submission raises unexpectedly, its outcome is unknown even if it may have committed; consult the local queue before retrying. The application does not implement a multi-product basket or automatically aggregate a purchase total.

Multi-product selection and deterministic aggregation are possible future scope, not part of this demo. Until then, a customer must supply a confirmed total or select an individual product; the agent does not infer a basket total from an unconfirmed budget. Ignored or duplicate Telegram updates produce sanitized operational events, and each conversation produces one terminal event without recording message content.

Before a real run, independently confirm provider access, data handling and an approved spending limit. Set `ARTEFACT_SOURCE_DIR`, `OPENAI_MODEL`, `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `OPENAI_BUDGET_USD`, `OPENAI_MAX_CALLS`, `OPENAI_INPUT_USD_PER_MILLION` and `OPENAI_OUTPUT_USD_PER_MILLION`; set `ENABLE_REAL_LLM=1` only after approval. Then use `docker compose up --build`. Prices must match the selected model and service tier. Each API call reserves a conservative estimated amount and one call in the persistent `agent_state` volume before sending. It fails closed when either limit would be exceeded. Inspect aggregate calls, reserved USD and provider-reported token counts with `docker compose run --rm agent python -m artefact.usage /state/agent.sqlite`. Reservations include a margin and are retained after failures; they are estimates, not invoice data or a guarantee against all billing differences. Do not delete the volume to reset a budget without a new approved budget. Never commit credentials or raw data. User messages and bounded prior replies are sent to the provider; `store=false` is requested.

Tests use fake transports and do not establish real Telegram delivery or model behavior. Update IDs are claimed persistently before processing, giving at-most-once handling: a crash or send failure after the claim may lose a reply, including when retrying an update after restart. Automatic resend is intentionally avoided because an ambiguous send failure could duplicate a message; the user may send a new question. Telegram delivery itself has no exactly-once guarantee. There is no complete rate limiting or seller messaging. Do not run a public or production bot with these limitations. Full weekday opening hours are not established in the approved sources used here.

## Local Codex feasibility demo

`python -m artefact.codex_demo` runs a host-only experiment using the already authenticated Codex CLI, without an API key or OAuth implementation. It always creates its own small synthetic dataset; it does not accept a challenge-data directory or connect Telegram. The bridge asks Codex for a schema-constrained JSON plan, validates and executes allowlisted functions in Python, and renders their results deterministically. This is structured-output orchestration, not the Responses API's native function-calling protocol. The Responses provider above remains available separately.

Install and sign in to the official Codex CLI first. Set `CODEX_DEMO_APPROVED=1`, a positive `CODEX_DEMO_MAX_CALLS`, and `CODEX_DEMO_STATE_PATH` to a writable local SQLite path. Run `python -m artefact.codex_demo` and enter one question per line. The persisted counter is a local call cap, not a measurement or guarantee of the plan's quota. Each data-backed turn uses at most one call; failed calls still consume a reservation. The CLI runs with a temporary empty working directory, read-only sandbox, ephemeral sessions, user configuration ignored, shell and other tool features disabled, web search disabled, and no API-key or Telegram-token environment variables forwarded. It uses the local Codex authentication normally without reading or exporting credentials.

This is a constrained feasibility experiment, not a security certification or a production customer-facing service. The CLI runs on the host, but inference sends prompts and tool results to the remote Codex service; it is not an offline model. Codex plan limits and access can change, the host needs the CLI and an authenticated session, and a command-disabled synthetic test does not prove all future versions immune to prompt injection. The standalone demo uses synthetic data; the host Telegram path was separately exercised with the original fictional baseline, as recorded in Plane.

## Host-only Codex Telegram test

`python -m artefact.codex_telegram` is an opt-in Windows-host test path for the original fictional challenge dataset. It does not move the Codex session to Docker or alter the Responses API setup. Set `ENABLE_CODEX_TELEGRAM=1`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_CHAT_ID` (one private chat ID), `ARTEFACT_DATA_DIR`, `CODEX_DEMO_STATE_PATH`, and a positive `CODEX_DEMO_MAX_CALLS` in the host process. The original six files must match their approved SHA-256 values. Use a dedicated, writable local SQLite state file outside the input directory and repository; it records update claims and aggregate Codex calls, not chat messages or secrets.

On Windows, `& .\scripts\setup-telegram.ps1` prompts for the token with masked input and locates a private chat after `/start`. It stores the two Telegram variables in the Windows user environment (the user registry, not a secret vault); it does not print or commit the token. `getUpdates` cannot work while the bot has a webhook or another long-polling consumer. A process already open before setup must explicitly reload the user environment values before starting the runtime.

Only private messages from the configured chat reach the model. The chat restriction is an experimental channel boundary; the approved fictional order lookup remains an exact, unique full-name match and is not authentication for real people. The local Codex subprocess disables shell tools, uses a read-only sandbox and does not receive the Telegram token or `OPENAI_API_KEY` through its environment. Only one poller should run per bot. Other chats and unsupported update types are ignored and acknowledged by advancing the bot's shared update offset; use a dedicated test bot to avoid consuming updates intended for another application. Operational SQLite paths inside the checkout or configured original-data directory are rejected. Update claims are at-most-once: a crash or send failure can lose a reply.

## CSV-first local administration (review candidate)

The local admin service accepts a UTF-8 CSV with exactly these column names (order may vary): `product_id,price_brl,name,category_id,description,stock_quantity,status,specs,created_at`. IDs and quantities are integers, prices use a decimal point with at most two fractional digits, status is `active`, `discontinued` or `coming_soon`, specs is a JSON object, date is ISO `YYYY-MM-DD`, and category IDs must exist in the original categories. CSV quoting must escape JSON quotes correctly. Maximum upload size is 1 MiB and 1,000 product rows. Duplicate IDs, malformed rows, unknown categories and negative prices reject the whole batch. This increment adds products; it does not edit existing IDs. Product descriptions and specifications with detected conflicts are flagged for review and remain conservatively masked in customer responses; independently valid price and stock remain usable.

In PowerShell, configure `ARTEFACT_SOURCE_DIR` to the original six-file directory and set a strong random `ARTEFACT_ADMIN_PASSWORD` (at least 16 characters) in the process environment without committing it. For a new installation only, set `ARTEFACT_ADMIN_INITIALIZE=1`, run `docker compose --profile admin up --build admin`, then unset the flag and recreate the admin container after initial setup. Open `http://127.0.0.1:8080`; HTTP Basic user is `admin`. The compose binding is restricted to the host loopback. This is a local demonstration, not an Internet-facing administration service. Stop with Ctrl+C; named volumes retain data. Do not remove volumes unless intentionally discarding their contents.

Upload a CSV, inspect the added product rows and field-level findings, record a human review, then publish. The home page shows version history and permits activation of an earlier version. Approval never occurs through the model. The initial version 0 is the unchanged baseline. SQLite staging and administrative history are in a dedicated volume unavailable to the agent. A separate catalog volume contains published versions only and is mounted read-only in the Docker agent. Each agent turn reads one active version transactionally, merges its products with the immutable baseline, and works without the admin process running. For host Codex, set `ARTEFACT_CATALOG_DB` to the absolute path of an accessible published catalog database; do not point it at the admin database. With this variable unset, the original baseline is used.

The two file-backed SQLite databases are attached in a single transaction using DELETE journal mode. Do not enable WAL for this setup: SQLite's multi-database atomic-commit conditions depend on a disk-backed main database and non-WAL journaling. The tests inject an exception before commit but do not simulate power loss or filesystem failure; crash recovery and backup/restore remain review and QA items. Basic authentication, Host/Origin checking and CSRF tokens protect this localhost demo; HTTP is not encrypted and does not provide a production identity system. SQLite paths configured on the host must be outside both the repository and the source directory. No upload content is executed or written to a user-controlled path.

Configurable seller contact, technical-review queue, XLSX/DOCX and AI-assisted import are not included in this increment. The store's previously documented contact values remain unchanged. Real customer data still requires proper authentication. Policy-summary publication permission remains a final submission gate.

### Conflict review, durability and remaining scope

Each scanner finding has a stable SHA-256 identifier derived from its batch and full finding (including field and evidence). Each exception requires an individual human justification; generic batch approval cannot replace these decisions. Correct an erroneous product by uploading a corrected CSV as a new batch: the old batch remains in history, and there is no button that can claim unchanged conflicting data was corrected. Approval binds the exact uploaded bytes, and publication recalculates findings and checks all decisions and the byte hash inside its write transaction. Accepted technical conflicts remain masked in the customer-facing catalog; independently valid prices and stock remain available. Administrative history records evidence, justifications, approvals and version activations. Activation requires a nonempty reason of at most 1,000 characters. Existing admin databases are migrated without deleting history or versions; old approved batches without the new binding must be reviewed again.

An unset `ARTEFACT_CATALOG_DB` intentionally selects the original baseline. Once a catalog path is configured, a missing database is an operational failure, not an implicit return to version 0. Initial creation requires explicit `ARTEFACT_ADMIN_INITIALIZE=1` and both administrative and catalog databases to be absent; unset this one-time flag immediately after initialization so loss of both volumes is not silently treated as a new installation; a missing one of the pair or invalid existing active version prevents startup. Preserve and back up both volumes together. The agent opens the published database read-only and cannot repair a hot journal; a query may fail safely until the administrative service recovers it. With both existing volumes present and `ARTEFACT_ADMIN_INITIALIZE` unset or `0`, restart the admin service with `docker compose --profile admin up -d admin`; its startup opens both existing files with SQLite `mode=rw`, attaches them, and reads their schemas to trigger SQLite recovery before the read-only preflight. If recovery fails, startup aborts; preserve both volumes and investigate rather than delete or reinitialize them. Recovery behavior depends on filesystem and volume semantics and needs deployment-specific QA.

The write connection sets SQLite rollback journals (`DELETE`) and `synchronous=FULL` for both attached databases, with `foreign_keys=ON` per connection; automated tests check the effective settings. SQLite documents atomic commits across attached disk databases when rollback journaling is used: https://www.sqlite.org/lang_attach.html. These guarantees assume the underlying Docker storage correctly implements locking, sync and durable filesystem operations. Tests cover concurrent writes, a reader during version changes and abrupt process termination before commit; they do not simulate real power loss, a host crash during commit, storage hardware failure, or restore from backup. Run those tests only on disposable environments. A review must assess the Docker storage implementation, cross-volume durability, hot-journal recovery and access controls for the intended deployment.

Human decision for M05: this increment accepts only the canonical product headers, in any order; arbitrary column mapping is deferred to a later evolution and does not block this PR. M05 is not a full pass. A later mapping step would require a UI for mapping and type validation, saved mappings and adversarial tests; estimate roughly 1–2 engineering days plus QA, subject to schema and UX decisions. M05 is not marked as passed. XLSX, DOCX and AI-assisted ingestion remain outside this PR.

### Public seller contact and technical review queue

The authenticated admin home allows changing or restoring the seller/store contact. The required format is `(DD) NNNN-NNNN` or `(DD) NNNNN-NNNN`; the default is `(67) 3341-4444`. The remote-agent number remains `(67) 3321-4500`. Contact changes and their prior values are recorded in the admin event history, while the current approved public value is committed atomically to the catalog projection. The agent reads the public value with its catalog snapshot and never mounts the admin database. The contact is independent of catalog-version rollback.

The optional technical-review queue records only product ID, one supported field, structured reason, catalog version, status and timestamps. It currently supports existing scanner conflicts on `brand`, `category_id`, `specs.keys` and `specs.strings`; it does not accept free text or store conversations. The agent permits a request only when the current message explicitly asks to register a review and identifies the product; both the agent and admin service validate the conflict, and the service also checks the active catalog version in its write transaction. An authenticated operator can view and complete cases in the admin panel. A successful response means only that the local case was persisted; no external message is sent.

To enable this optional internal channel, supply the same high-entropy ASCII token (32–128 characters from letters, numbers, `_` and `-`) as `ARTEFACT_REVIEW_TOKEN` to both services; generate it locally and never commit or print it. Set `ARTEFACT_REVIEW_URL=http://admin:8080/internal/reviews` for the Compose agent, or `http://127.0.0.1:8080/internal/reviews` for the host Codex process. The client accepts only these local service destinations (also `localhost`), disables proxies and redirects, and has a short timeout. With neither variable configured, review submission is disabled; configure URL and token together for the agent. The endpoint permits authenticated creation only and does not expose admin reads or staging; the agent does not mount `admin_data`. The panel still requires its separate admin password, Host/Origin checks and CSRF for operator actions. The internal connection is plaintext on the local Docker network; the token and channel are appropriate only for this local demonstration, not an untrusted network. The admin service must be running to register a case; failure returns a generic response without claiming registration. Existing catalog and contact answers do not require the admin process while the catalog volume remains available.

Technical-review registration uses a conservative deterministic check on the current message: an affirmative registration request and an explicitly identified product are required. Questions and negations prompt clarification. Product IDs must be labeled as product IDs; order numbers and prices are not product identifiers. If a product has multiple conflicting fields, the customer must name exactly one supported detail (marca, categoria, teclas or cordas); the model cannot pick it on the customer's behalf. Ambiguous phrasing asks for clarification and does not create a case. This conservative rule can ask for clarification even when a human might infer the intent.

Repeated requests for the same product, field and catalog version return the existing open case. The lookup and insertion execute under the same SQLite `BEGIN IMMEDIATE` transaction, serializing concurrent writers across the attached databases. A partial lookup index is non-unique so installations that already contain duplicate open cases are not silently modified or prevented from starting; if such legacy duplicates exist, the oldest is returned and operators can close the others. A new case can be created after the prior one is completed. HTTP remains unencrypted inside the local demonstration network; no external service is contacted.
